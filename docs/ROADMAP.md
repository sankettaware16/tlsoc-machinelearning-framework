# Roadmap

The spec's own phasing (SPEC_DIGEST §12) assumes a funded team and a live
enterprise estate. This roadmap re-sequences the same content for how the project
is actually being built: **offline-first, vertical slices, each phase ending in
something runnable and measurable.**

Guiding rule: **never build a layer that cannot be exercised end-to-end.** A
half-built feature platform with no use case on top of it is unverifiable work.
So the first milestone deliberately drives one use case all the way from log file
to explained alert, on a thin version of every layer, and later phases widen
rather than deepen.

Phases are ordered by dependency, not calendar-dated.

## Phase 1 — First vertical slice: web_recon (UC-02) offline ✅ *complete*

**Exit met:** `soc-ml backtest --uc web_recon --input <logs>` produces scored,
explained findings with a metrics report — no Kafka, Redis, or ES.

- [x] `docs/NAMING.md`: slug + spec-ID + title naming standard, full catalog,
      CI-enforced (`tests/test_naming.py`) — D-016
- [x] `baseline/`: Environment Profile v1 — path IDF, UA frequency, served
      extensions, population feature stats (p50/p99); JSON-persisted artifact
- [x] `features/`: streaming tumbling-window builder (5m per entity, bounded
      memory, watermark close, evidence retention) — D-017
- [x] `models/`: `isolation_forest` + `lof_novelty` wrappers, uniform
      fit/score/save/load, deterministic fits
- [x] `usecases/web_recon.py`: spec features + max-fusion + gate
      (fused pct ≥ 99.7, evidence floor ≥5 events / ≥3 paths)
- [x] `fusion/`: 1001-point percentile calibration + the severity formula
- [x] `explain/`: population-context attributions + deterministic narrative +
      verbatim evidence lines
- [x] `alerting/file` sink (ECS-aligned, naming triple in every alert)
- [x] `evaluation/`: backtest harness — chronological split, **corpus hygiene
      (p99.9 clip + top-0.1% drop, FR-56)**, deterministic **canary** injected
      into scoring only (FR-58), every score recorded
- [x] `soc-ml backtest` CLI (fails the run if the canary is missed)
- [x] 92 tests passing; e2e test gates on canary detection + FP budget

**Thesis proven on real data:** on 300k events of live production nginx traffic the
slice detected a genuine directory-enumeration attacker (203.0.113.199, ~150
req/5min, ~95 never-served paths, ~100×404) plus the canary — zero literal
thresholds anywhere. Deferred within-phase: generic `StateStore` impl (build
when the live loop needs it), PR-AUC (needs SAIF ground truth, Phase 3),
`orjson` ingest speedup (D-017).

**Carried forward:** raw alert volume on the real run (9 alerts/2h, 6 from the
one attacker) is the alert-storm shape that Phase 3's campaign folding and
progressive alerting exist to collapse — see D-017.

- [x] `detection/scorer.py`: shared scoring — backtest and live run identical

- [x] `detection/runtime.py`: live loop — tail → window → score → dedup → budget
      → sink, checkpoint+resume, health JSON, graceful SIGTERM drain, cold-start
- [x] `detection/dedup.py` + `detection/budget.py`: per-entity fold + daily
      per-server budget → digest (FR-34)
- [x] `drift/psi.py`: PSI vs training reference, hourly, retrain trigger (FR-51)
- [x] Modes observe/shadow/live, per-use-case (staged cold-start)
- [x] `soc-ml train` / `run` / `promote` / `status` (+ `--rollback`)
- [x] `DEPLOYMENT.md` + systemd unit + config runtime knobs

**Deferred (Phase 2 remainder, needed at multi-use-case scale, not for single-UC
deploy):** cadence-ladder *scheduler* (cron/timer suffices now); KS/ADWIN
(PSI covers the trigger); the ≥72 h automated challenger soak (manual promote is
the gate today); incident-window quarantine (no confirmed-incident store yet).

**Known gap carried to Phase 3:** single-detector alert volume exceeds the
≤3/day budget until false-positive suppression (UC-04 crawlers, UC-12 campaigns,
corroboration) lands. The daily budget bounds it in the meantime — see D-018.

## Phase 3 — Tier-1 detection complete

**Exit:** the five Tier-1 use cases run together, and fusion demonstrably reduces
alert volume versus running them independently.

- [ ] UC-04 (bot/crawler) — **build before UC-02 tuning finishes**; it produces
      the known-crawler cluster and human-likeness features that suppress false
      positives in UC-02/06/15
- [ ] UC-01 (credential stuffing) — Half-Space Trees streaming layer + coordination layer
- [ ] UC-06 (scraping) — session autoencoder 16-8-4-8-16
- [ ] UC-07 (exfiltration) — path-family GMM + quantile forecaster + β-VAE drip
- [ ] Full fusion: corroboration, fleet-simultaneity suppression, campaign
      folding, rate governance
- [ ] SAIF v1: attack generators for each Tier-1 use case + regression gating

**Dependency note:** UC-04 is the FP-suppression backbone. It is ranked 3rd by
the spec but should be built 2nd.

## Cross-cutting, from Phase 0 onward

Not a phase — these run continuously and are release-blocking at every phase.

- **The threshold lint** (FR-62). It must exist before use cases do, or literal
  thresholds will creep in and G1 dies quietly.
- **Contract tests** against the sample logs.
- **`benign-true-positive`** as a first-class verdict from the first alert schema.
- **Journal discipline** — every non-obvious decision recorded in `JOURNAL.md`.

## Sequencing risks

| Risk | Mitigation |
|---|---|
| Building the feature platform "properly" before any use case exists | Phase 1 is a vertical slice; the platform grows to fit real demand |
| UC-04 built late, so UC-02/06 drown in crawler false positives | UC-04 promoted to build-2nd in Phase 3 |
| Lifecycle bolted on after use cases | Phase 2 precedes the bulk of the catalog |
| Enterprise stack assumptions leaking into the core | Phase 6 last; NFR-07 tested on a fresh install |
| PyTorch becoming a hard dependency | cheap tiers first (4-gram LM), deep models behind extras + config switch |
| Cold start (2–8 weeks) discovered at deployment time | staged protocol built in Phase 2 and exercised offline via replay |
